This specification defines interop profiles: normative bindings that map concrete agent runtimes and agent protocols onto the Agent Trust Protocol's runtime-agnostic trust plane. Four profiles are defined — MCP (Model Context Protocol tool servers), A2A (agent-to-agent invocation), Local Agents (in-process runtimes and frameworks), and Multi-Agent Orchestration (crews, graphs, and stateful sessions). Each profile specifies how the runtime's native operations are expressed as Capability Requests, how Policy Decisions are enforced in that runtime, and what evidence is emitted.

The design rule shared by all profiles is: adapters map, profiles decide. An adapter translates runtime-native operations into the standard envelope; it MUST NOT embed policy of its own.

Identity: did:atp. Trust: ATP Agent Trust. Envelopes: Capability Request & Policy Decision. Vectors: ATP Conformance & Interoperability.

This document is an early draft work product of the Agent Trust Protocol (ATP) Community Group. It is not a W3C Standard nor on the W3C Recommendation track. The profiles are seeded from running reference adapters (MCP server wrapper, A2A bridge, and framework integrations); their bindings are provisional.

As well as sections marked as non-normative, all authoring guidelines, diagrams, examples, and notes in this specification are non-normative. Everything else is normative.

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as described in BCP 14 [[RFC2119]] [[RFC8174]] when, and only when, they appear in all capitals.

Requirements Common to All Profiles

A conforming adapter, in any profile, MUST:

  1. Bind identity: resolve the acting agent to a did:atp identifier before any guarded operation; unidentifiable callers are treated as trust level UNKNOWN.
  2. Envelope every guarded operation: express it as a Capability Request with target.kind and target.sensitivity populated per the profile's mapping table.
  3. Enforce the decision: execute only on allow (discharging obligations), rate-limit on throttle, park on require_approval, and block on deny. The adapter MUST NOT reinterpret or soften a decision.
  4. Emit evidence: record the request, decision, and outcome to an audit store conforming to Audit-Store Integrity, correlated by requestId.
  5. Stay policy-free: all authorization logic lives in profiles and the policy decision point; a hard-coded allow/deny in adapter code is non-conformant.

Profile: MCP

This profile binds ATP to Model Context Protocol servers and clients. An ATP-secured MCP server interposes the trust plane between tool discovery/invocation and tool execution.

MCP operationCapability Request mapping
tools/list action: "read", target: {kind: "resource", type: "mcp-tool-catalog"}. The server SHOULD filter the returned catalog to tools the caller could be allowed to invoke.
tools/call action: "execute", target: {kind: "tool", id: <tool name>, type: <tool category>}, with tool arguments (or their digest) as arguments.
resources/read action: "read", target: {kind: "resource", id: <uri>}.

The caller's DID MUST be established at session setup (e.g. a signed handshake carrying the client's did:atp identifier) and pinned for the session's lifetime. A deny MUST surface as an MCP error result — not a silent empty result — with the decision's reason in the error message and no partial tool output.

Profile: A2A

This profile binds ATP to agent-to-agent invocation: one agent (the caller) requesting work from another (the callee), directly or via a discovery/bridge layer.

  • An invocation MUST be enveloped as action: "execute", target: {kind: "agent", id: <callee DID>, type: "a2a-invocation"}.
  • Both sides evaluate. The caller's runtime evaluates whether the caller may delegate to the callee; the callee's runtime independently evaluates whether to accept work from the caller. Either side's deny blocks the invocation.
  • Trust is presented, not asserted: the caller SHOULD present an ATP Trust Credential; the callee MUST verify it before using its trust level.
  • Message payloads exchanged after an allow SHOULD be signed with the sender's did:atp keys; discovery listings SHOULD carry each agent's DID so trust can be checked before first contact.
  • Delegation depth is part of context: a request made on behalf of another agent MUST identify the originating subject so the PDP can bound transitive delegation.

Profile: Local Agents

This profile binds ATP to in-process runtimes — agent frameworks and SDKs where tools are plain functions (e.g. LangChain-style tools, OpenClaw/NemoClaw skills, or custom runtimes). The binding is a tool wrapper: a higher-order function that envelopes each call of the wrapped tool.

  • Registration: the runtime registers each agent with the trust plane at startup, obtaining a did:atp identifier bound to the runtime instance (runtime binding).
  • Every wrapped-tool invocation MUST produce a Capability Request with target.kind: "tool" and a profile-declared type (e.g. shell, http, filesystem, database, messaging) so policies can be written against action classes rather than tool names.
  • Wrapping MUST be fail-closed: if the trust plane is unreachable, the wrapper MUST deny (or queue for approval), never fall through to raw execution.
  • Batch wrapping (securing a whole toolset at once) MUST be semantically identical to wrapping each tool individually.

Profile: Multi-Agent Orchestration

This profile binds ATP to orchestrated collections of agents — crews, graphs, and stateful sessions — where which actions are permitted depends on where the workflow currently is.

  • Session states: an orchestration session moves through declared lifecycle states; the reference state machine is planning → executing → communicating → completed. The current state MUST be supplied to the PDP as context.sessionState, and state transitions MUST themselves be evidenced events.
  • State policies: a state policy maps each state to the action classes permitted in it (e.g. no tool execution during planning; messaging only during communicating; read-only during completed). State policies are profile data consumed by the PDP — never hard-coded in the orchestrator.
  • Topology validation: before a crew or graph runs, the orchestrator SHOULD validate the agent topology (who may hand off to whom) against policy, so disallowed edges fail at plan time rather than mid-run.
  • Per-member identity: every member agent holds its own DID and trust level; a crew MUST NOT act under a single shared identity.

Profile Registry and Extensions

New runtimes are supported by authoring a new profile, not by extending adapters ad hoc. A registered profile MUST provide: (1) a mapping table from runtime-native operations to Capability Request fields, (2) the enforcement semantics for each decision kind in that runtime, and (3) the identity-binding mechanism. Profiles MAY register additional target.type values and scope strings per the scope vocabulary rules.

Whether profile registration lives in this document, a CG registry page, or an IANA-style registry is open for discussion.

Security & Privacy Considerations

Adapters are the trust plane's attack surface: a bypassed wrapper is a bypassed protocol. Runtimes SHOULD make the wrapped path the only path to tool execution. In A2A, mutual evaluation prevents a compromised caller from relying on the callee's laxity (and vice versa). In orchestration, per-member identity keeps audit evidence attributable when one member of a crew misbehaves.
