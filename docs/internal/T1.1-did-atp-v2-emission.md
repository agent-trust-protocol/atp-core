# T1.1 — identity-service did:atp v2 emission

Status: **first increment landed.** This note records what changed and what is
deliberately deferred.

## Context

`packages/identity-service` previously minted the **legacy v1** identifier
`did:atp:<multibase>` (just a multibase-encoded Ed25519 public key — no domain,
no `e1_`/`pq1_` binding fingerprints). The authoritative method spec
(`docs/specs/did-atp/index.html`) and the SDK (`packages/sdk/src/utils/did.ts`,
`DidAtp`) define a **v2** identifier:

```
did:atp:<domain>:<path...>:e1_<43 base64url>:pq1_<43 base64url>
```

- `e1_` = RFC 7638 JWK thumbprint of the Ed25519 binding key (the `did:wba`
  classical binding).
- `pq1_` = RFC 7638 JWK thumbprint of the ML-DSA-65 (FIPS 204) binding key,
  represented as an RFC 9964 `AKP` JWK.

## What landed (this increment)

1. **Real hybrid key material.** `CryptoUtils.generateQuantumSafeKeyPair()` now
   generates an independent Ed25519 keypair **and** an independent, genuine
   **ML-DSA-65** keypair (1952-byte public key). Previously the "hybrid"
   provider from `@atp/shared` paired Ed25519 with Ed25519 (because
   `defaultPQCConfig.signatureAlgorithm === ED25519`), so no post-quantum key
   was ever produced. We now drive a dedicated `CryptoAgilityManager`
   configured for `CRYSTALS_DILITHIUM` (ML-DSA-65) to obtain the PQ key. The
   combined `pqcPublicKey` is encoded as `Ed25519(32) || ML-DSA-65(1952)`.
   No new crypto primitives were introduced — this reuses the existing
   `@noble`-backed providers in `packages/shared/src/crypto/pqc-crypto.ts`.

2. **v2 identifier construction.** New helpers in
   `packages/identity-service/src/utils/crypto.ts`:
   `base64url`, `jwkThumbprint`, `e1Fingerprint`, `pq1Fingerprint`,
   `buildAtpV2Did`, and `extractBindingPublicKeys`. These mirror the SDK's
   `CryptoUtils`/`DidAtp` byte-for-byte (verified: a DID minted by
   identity-service parses and validates with `DidAtp.parse` / `DidAtp.isValid`).
   `generateQuantumSafeDID()` now emits a v2 path-type DID for hybrid keys, and
   falls back to the legacy v1 form only for classical-only registration.

3. **Call site.** `IdentityService.registerDID()` now:
   - emits the v2 identifier;
   - publishes the ML-DSA-65 binding as a spec-shaped `JsonWebKey` verification
     method with an RFC 9964 `AKP` JWK (`{kty:'AKP', alg:'ML-DSA-65', pub}`)
     whose RFC 7638 thumbprint equals the `pq1_` path segment;
   - bumps `metadata.version` to `2.0.0` and records
     `metadata.additionalInfo.didMethodVersion` = `'v2'` (or `'v1'` on the
     classical fallback) so emitted documents are self-describing.

4. **Tests.** `packages/identity-service/src/services/__tests__/identity.test.ts`
   gained coverage asserting: the v2 syntax (`ATP_V2_RE`), that the `pq1_`
   segment recomputes from the document's AKP JWK (1952-byte key), and that
   classical-only registration falls back to v1. All identity-service tests
   pass.

## Deliberately deferred (not in this increment)

These are larger and not required for correct v2 *emission*; they are tracked
here for a follow-up:

1. **Full dual-proof DID Document.** The SDK's `DidAtpDocument.create` produces
   a `did.json` with **both** proofs — the `eddsa-jcs-2022` Data Integrity
   proof and the RFC 9964 ML-DSA-65 JWS (`atpPqProof`). identity-service's
   `registerDID` still builds the document in its own legacy shape (rich
   `assertionMethod`/`keyAgreement`/`capability*` arrays, `Ed25519VerificationKey2020`
   classical VM, no signed proofs). It does not yet attach either proof.
   Migrating identity-service to construct/sign the document via the SDK's
   `DidAtpDocument` (or to inline equivalent dual-proof signing) is the next
   step, so that documents served by this service pass
   `DidAtpDocument.verify()` and the SDK's `DidAtpResolver`.

2. **Resolution / URL transform.** `IdentityService.resolveDID` is still a
   local-store / universal-resolver lookup keyed by DID string. It does not yet
   implement the `did:wba`-style path-to-URL transform + dual-binding
   verification that `packages/sdk/src/utils/resolver.ts` (`DidAtpResolver`)
   provides. For v2 DIDs served over HTTPS, resolution should go through (or
   mirror) `DidAtpResolver`.

3. **`rotateKeys`.** Key rotation still rewrites a v1-style VM in place. Per the
   spec, rotating *either* binding key changes the DID (both fingerprints are in
   the path), so rotation must mint a **new** DID + document (cf.
   `DidAtpDocument.rotate`) rather than updating in place. This is unchanged
   here.

4. **Sharing the SDK implementation directly.** identity-service is **not** a
   workspace consumer of `atp-sdk` (different package name, no path alias, not
   in `node_modules`), so importing `DidAtp`/`DidAtpDocument` from the SDK at
   runtime is not currently wired. The v2 helpers were therefore added to
   identity-service's own `CryptoUtils`, kept byte-compatible with the SDK and
   covered by a cross-compatibility check. A cleaner long-term fix is to publish
   the did:atp primitives from `@atp/shared` (which both the SDK and
   identity-service already depend on) and have both import from there, removing
   the duplication.

## Verification

- `npx jest --config jest.config.cjs --testPathPattern identity-service` — all
  pass (including the new v2 assertions).
- A throwaway cross-compat check confirmed `DidAtp.parse(did)` /
  `DidAtp.isValid(did)` accept the identity-service-minted DID.
- The runnable proof of concept in `/proof` exercises the full spec design
  (FIPS 204 sizes, hybrid identifier, dual-binding resolution, defense in depth,
  method-agnostic trust credential) against the SDK implementation.
