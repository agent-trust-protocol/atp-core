This specification defines the two envelopes at the heart of the Agent Trust Protocol's trust plane: the Capability Request — a standard, runtime-agnostic object through which an agent asks to perform an action (a tool call, an agent-to-agent invocation, a resource access, or a delegated action) — and the Policy Decision — the normalized authorization result (allow, deny, throttle, or require_approval) returned by a policy decision point, carrying a reason code, a policy reference, and any obligations.

Together with agent identity (did:atp) and attested trust (ATP Trust), these envelopes answer the protocol's second question: what action is being requested, under which policy context, and what was decided?

Agent identity is defined by the did:atp DID Method. The trust model consumed during evaluation is defined by ATP Agent Trust. Evidence emitted about a decision is anchored per ATP Conformance & Interoperability. Runtime-specific mappings of this envelope are defined by ATP Interop Profiles.

This document is an early draft work product of the Agent Trust Protocol (ATP) Community Group. It is not a W3C Standard nor on the W3C Recommendation track. The envelope fields below are seeded from a running reference implementation and are provisional; Community Group members are invited to challenge field names, the scope vocabulary, and the decision taxonomy.

As well as sections marked as non-normative, all authoring guidelines, diagrams, examples, and notes in this specification are non-normative. Everything else is normative.

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as described in BCP 14 [[RFC2119]] [[RFC8174]] when, and only when, they appear in all capitals.

Model

A capability subject (an agent, identified by a DID) submits a Capability Request to a policy decision point (PDP). The PDP evaluates the request in a policy context — the subject's verified trust level, credentials, the target's sensitivity, and environmental conditions — and returns exactly one Policy Decision. An enforcement point (typically the tool wrapper or runtime adapter) executes or blocks the action accordingly and emits evidence. Long-lived grants are represented as Capability Tokens so that repeated requests need not re-consult the PDP for the token's validity window.

The Capability Request

A Capability Request is a JSON object with the following members:

MemberReq.Description
subjectMUST DID of the agent requesting the action.
actionMUST The requested action, drawn from the scope vocabulary or a profile-registered action string.
targetMUST Object identifying what the action operates on: kind (one of tool, agent, resource, delegation), id, and OPTIONAL type and sensitivity (public | internal | confidential | restricted).
contextSHOULD The policy context under which evaluation is requested.
argumentsMAY Action arguments, or a digest of them when the arguments are large or sensitive.
justificationMAY Human- or agent-readable rationale, surfaced to reviewers when the decision is require_approval.
requestIdMUST Unique identifier for correlating the request, decision, and emitted evidence.
timestampMUST RFC 3339 timestamp of submission.

  "requestId": "req_9f2c1e",
  "subject": "did:atp:agents.example.com:e1_...:pq1_...",
  "action": "read",
  "target": {
    "kind": "tool",
    "id": "database_query",
    "type": "database",
    "sensitivity": "internal"
  },
  "context": {
    "organizationId": "org_test",
    "sessionState": "executing"
  },
  "timestamp": "2026-07-24T12:00:00Z"
}
      
{
  "requestId": "req_51ab77",
  "subject": "did:atp:agents.example.com:researcher...",

Scope Vocabulary

The base scope vocabulary is: read, write, execute, admin, identity:read, identity:write, vc:issue, vc:verify, vc:revoke, permission:grant, permission:revoke, audit:read, audit:write. Interop profiles MAY register additional <namespace>:<verb> scopes; implementations MUST treat unrecognized scopes as unmatchable (and therefore, under deny-by-default, denied).

Policy Context

The policy context is the evaluation input alongside the request itself. It carries at least the subject's trustLevel (obtained from a verified ATP Trust Credential or a trusted scoring engine), the subject's presented credentials, and MAY carry an organizationId, a sessionState (see Interop Profiles), and environmental attributes (time, origin, rate counters). A PDP MUST NOT accept a caller-asserted trust level that is not backed by verification.

The Policy Decision

A PDP MUST return exactly one Policy Decision per Capability Request, with the following members:

MemberReq.Description
decisionMUST One of allow, deny, throttle, require_approval.
reasonMUST Human-readable explanation of the outcome.
reasonCodeSHOULD Stable machine-readable code (e.g. NO_MATCHING_RULE, TRUST_BELOW_THRESHOLD, POLICY_DISABLED, RATE_EXCEEDED, EVALUATION_ERROR).
policyRefSHOULD Identifier (and version, if versioned) of the policy and rule that produced the decision.
obligationsMAY Array of obligations the enforcement point MUST discharge when acting on an allow: log, alert, mfa_required, time_limit, usage_limit, throttle.
requestIdMUST Echo of the request's requestId.
timestampMUST RFC 3339 timestamp of evaluation.

A conforming PDP MUST:

  • apply deny-by-default: a request matching no allow rule MUST yield deny with reasonCode: "NO_MATCHING_RULE";
  • fail closed: an evaluation error MUST yield deny with reasonCode: "EVALUATION_ERROR", never allow;
  • resolve rule conflicts deterministically, with deny winning ties at equal priority;
  • evaluate rule conditions only in a safe-expression sandbox, and reject (not evaluate) policy expressions outside the sandboxed grammar.

An enforcement point receiving throttle MUST delay or rate-limit the action per the accompanying obligation; receiving require_approval, it MUST NOT execute the action until an out-of-band approval is recorded, and MUST treat approval timeout as deny. 

{
  "requestId": "req_9f2c1e",
  "decision": "allow",
  "reason": "VERIFIED trust level permits internal database reads",
  "reasonCode": "RULE_MATCHED",
  "policyRef": "policy:org_test/data-access@3#rule-7",
  "obligations": [
    { "type": "log" },
    { "type": "usage_limit", "limit": 100, "window": "PT1H" }
  ],
  "timestamp": "2026-07-24T12:00:00Z"
}

Capability Tokens

A Capability Token represents a standing grant so that repeated identical requests need not re-consult the PDP. A token MUST carry id, issuer, subject, audience, scopes (from the scope vocabulary), issuedAt, and expiresAt; it MAY carry resource, conditions, and notBefore. Tokens MUST be integrity-protected (signed by the issuer), MUST be validated for signature, audience, and temporal validity before use, and MUST be revocable by the issuer. A token never overrides a deny produced by a live evaluation of the same request.

The reference implementation encodes tokens as JWTs. Whether to mandate JWT, allow SD-JWT / VC-based encodings, or leave encoding to interop profiles is open for CG discussion.

Security & Privacy Considerations

The decision taxonomy is deliberately closed: introducing vendor-specific decision values would fragment enforcement semantics, so extensions MUST be expressed as obligations, not new decision kinds. Because arguments may contain sensitive data, requests SHOULD carry digests rather than raw values when the PDP does not need them, and emitted evidence MUST NOT embed raw secrets. Deny-by-default and fail-closed evaluation are security-critical and are exercised by the conformance suite.
