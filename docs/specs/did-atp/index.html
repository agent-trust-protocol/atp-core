This document is the normative reference for the did:atp v2 rebuild in packages/sdk. It consolidates and supersedes the DID-method portions of the legacy docs/W3C_ATP_SPECIFICATION.md (ATP Specification v1.0), which remains in place unmodified for historical reference.

Abstract

The did:atp method provides decentralized, cryptographically verifiable, quantum-safe identities for AI agents participating in the Agent Trust Protocol (ATP). It combines classical Ed25519 keys with post-quantum CRYSTALS-Dilithium keys in a hybrid scheme, and binds agent identities to ATP trust scoring, verifiable credentials, and audit infrastructure.

1. Conformance

The key words must, must not, required, should, should not, recommended, may, and optional in this document are to be interpreted as described in RFC 2119.

2. Method Syntax

The method name is atp. A conforming DID has the form:

did:atp:<network>:<unique-identifier>
  • <network> — one of mainnet, testnet, or devnet. The network segment is required; implementations must not emit or accept two-segment did:atp:<id> identifiers.
  • <unique-identifier> — the multibase (base58btc, z-prefixed) encoding of the agent's Ed25519 public key fingerprint.

Example:

did:atp:mainnet:z6MkukG4UkfY7RDATt51tYQHJuQSd2XstDanvqSbJHQyxdvu

3. DID Document Structure

A conforming did:atp DID document:

  • must include both https://www.w3.org/ns/did/v1 and https://atp.dev/ns/v1 in @context;
  • must contain an Ed25519 verification method of type Ed25519VerificationKey2020;
  • must contain a post-quantum verification method of type DilithiumVerificationKey2024;
  • must reference both keys in authentication;
  • should include an ATPGateway service endpoint.
{
  "@context": [
    "https://www.w3.org/ns/did/v1",
    "https://atp.dev/ns/v1"
  ],
  "id": "did:atp:mainnet:z6MkukG4UkfY7RDATt51tYQHJuQSd2XstDanvqSbJHQyxdvu",
  "verificationMethod": [{
    "id": "#key-1",
    "type": "Ed25519VerificationKey2020",
    "controller": "did:atp:mainnet:z6MkukG4UkfY7RDATt51tYQHJuQSd2XstDanvqSbJHQyxdvu",
    "publicKeyMultibase": "z6MkukG4UkfY7RDATt51tYQHJuQSd2XstDanvqSbJHQyxdvu"
  }, {
    "id": "#key-2",
    "type": "DilithiumVerificationKey2024",
    "controller": "did:atp:mainnet:z6MkukG4UkfY7RDATt51tYQHJuQSd2XstDanvqSbJHQyxdvu",
    "publicKeyMultibase": "z8FqT3Xz9Bc2YPqQfZvvKqVxGRSqwELBv3d6umccPsQKQvBNL"
  }],
  "authentication": ["#key-1", "#key-2"],
  "assertionMethod": ["#key-1"],
  "keyAgreement": ["#key-1"],
  "service": [{
    "id": "#atp-gateway",
    "type": "ATPGateway",
    "serviceEndpoint": "https://gateway.atp.example.com"
  }]
}

4. DID Operations

4.1 Create (Register)

POST /identity/register
Content-Type: application/json

{
  "publicKey": "z6MkukG4UkfY7RDATt51tYQHJuQSd2XstDanvqSbJHQyxdvu",
  "metadata": {
    "name": "AI Assistant Bot",
    "capabilities": ["text-generation", "data-analysis"]
  }
}

4.2 Resolve

GET /identity/resolve/{did}

Resolution must return a W3C-conformant DID resolution result. Unknown DIDs must produce error DID_NOT_FOUND (−32001).

4.3 Update

PUT /identity/update/{did}
Authorization: DID-JWT

{
  "verificationMethod": [...],
  "service": [...]
}

Updates must be authenticated with a DID-JWT signed by a key currently authorized for authentication on the document.

4.4 Deactivate

Implementations must support DID deactivation (supports the GDPR right to be forgotten). A deactivated DID must resolve with deactivated: true document metadata and must not be reactivatable.

5. Cryptographic Requirements

5.1 Hybrid Signature Scheme

Implementations must support hybrid signatures combining:

  1. Classical: Ed25519;
  2. Post-Quantum: CRYSTALS-Dilithium (Dilithium3 / ML-DSA-65).

5.2 Signature Format

Proofs must use the HybridSignature2024 JSON structure:

{
  "type": "HybridSignature2024",
  "created": "2024-01-15T12:00:00Z",
  "verificationMethod": "did:atp:mainnet:z6Mk...#key-1",
  "proofPurpose": "authentication",
  "classical": {
    "algorithm": "Ed25519",
    "signature": "base64url..."
  },
  "postQuantum": {
    "algorithm": "Dilithium3",
    "signature": "base64url..."
  }
}

5.3 Key Rotation

Agents must support key rotation with a minimum grace period of 24 hours during which signatures by the previous key remain verifiable.

6. Error Codes

Errors must use JSON-RPC 2.0 error objects with these codes:

CodeNameDescription
−32001DID_NOT_FOUNDDID does not exist
−32002INVALID_SIGNATURESignature verification failed
−32003INSUFFICIENT_TRUSTTrust level too low
−32004CREDENTIAL_EXPIREDCredential has expired
−32005QUANTUM_SIG_REQUIREDPost-quantum signature required

7. Security and Privacy Considerations

  • Identity spoofing is prevented by hybrid cryptographic signatures.
  • Replay attacks are prevented via timestamps and nonces (see the shared nonce service).
  • Quantum attacks are mitigated by the mandatory Dilithium component.
  • DIDs are pseudonymous by default; agents may use pairwise DIDs, and zero-knowledge proofs should be used for sensitive claims.
