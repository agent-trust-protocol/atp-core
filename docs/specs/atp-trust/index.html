This specification defines an agent trust scoring model and a TrustCredential: the trust score for an AI agent, issued and verified as a W3C Verifiable Credential [[VC-DATA-MODEL-2.0]]. The trust score is a single value in the interval [0, 1] derived from four weighted factors. The TrustCredential expresses that score as a credential whose integrity is secured by a Data Integrity proof using the eddsa-jcs-2022 cryptosuite [[VC-DI-EDDSA]], optionally paired with a post-quantum ML-DSA-65 JWS [[RFC9964]].

Trust scoring and Verifiable Credentials previously existed in ATP as decoupled mechanisms: a score was computed locally and never issued in a portable, verifiable form. This specification couples them, so that a relying party can verify a trust claim made by a third-party assessor without re-running the assessment and without trusting the transport.

The eddsa-jcs-2022 proof and the optional ML-DSA-65 JWS use the same construction as the did:atp DID Document [[?DID-CORE]], so proof vectors are consistent across ATP artifacts.

This document is a draft work product of the Agent Trust Protocol (ATP) Community Group. It is not a W3C Standard nor on the W3C Recommendation track. Publication as a Community Group Report does not imply endorsement by W3C or its Membership.

This specification is a companion to the did:atp DID Method specification. It reuses that method's classical (eddsa-jcs-2022) and post-quantum (ML-DSA-65 JWS) integrity mechanisms, but is otherwise DID-method-agnostic: any issuer and subject identified by a resolvable DID MAY participate.

Credential status / revocation (e.g. a status-list mechanism) is not defined by this version and is an open item. See Open Items and Conformance Gaps.

As well as sections marked as non-normative, all authoring guidelines, diagrams, examples, and notes in this specification are non-normative. Everything else is normative.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted as described in BCP 14 [[RFC2119]] [[RFC8174]] when, and only when, they appear in all capitals.

Trust Scoring Model

A trust score is a number in the interval [0, 1] computed from four trust factors, each itself a number in [0, 1]. An assessor MUST compute the trust score as the weighted sum of the four factors, and the four weights MUST sum to 1.

FactorMeaningDefault weight
interactionScoreVolume of interaction history.0.25
recencyScoreTime-decayed recency of interactions.0.25
credentialScoreVerified credentials held by the subject.0.30
successScoreSuccess rate of past interactions.0.20

An assessor MAY override the default weights, but the resulting weights MUST still sum to 1, and any non-default weighting SHOULD be disclosed to relying parties. An assessor MUST also report a confidence value in [0, 1] indicating how much data informed the score; relying parties SHOULD treat a low-confidence high score with caution.

Each trust score MUST be mapped to exactly one trust level for coarse-grained policy decisions:

LevelScore range
UNKNOWNno history
BASIC0.00 – 0.25
VERIFIED0.25 – 0.50
TRUSTED0.50 – 0.75
PRIVILEGED0.75 – 1.00

The TrustCredential VC Profile

A TrustCredential is a W3C Verifiable Credential [[VC-DATA-MODEL-2.0]] that attests a trust score about a subject agent. A conforming TrustCredential MUST satisfy all of the following:

  • Its @context MUST include the VC v2 base context https://www.w3.org/ns/credentials/v2.
  • Its type MUST include both VerifiableCredential and TrustCredential.
  • Its issuer MUST be the identifier (a DID [[?DID-CORE]]) of the assessing trust service.
  • Its credentialSubject MUST contain: id (the subject agent's DID), trustScore, trustLevel, factors (the four factor scores), confidence, and assessedAt (an ISO-8601 timestamp).
  • It MUST carry a Data Integrity proof whose type is DataIntegrityProof and whose cryptosuite is eddsa-jcs-2022 [[VC-DI-EDDSA]], with proofPurpose assertionMethod.
  • For post-quantum assurance it SHOULD additionally carry an atpPqProof: an RFC 9964 [[RFC9964]] compact JWS with algorithm ML-DSA-65 over the same unsecured credential.

Proof construction

The eddsa-jcs-2022 proof MUST be computed exactly as for an ATP DID Document: canonicalize the proof configuration and the unsecured credential with JSON Canonicalization Scheme [[RFC8785]], hash each with SHA-256, sign the concatenation sha256(JCS(config)) || sha256(JCS(credential)) with the issuer's Ed25519 key, and encode the signature as a multibase base58-btc proofValue (the z prefix). Verifiers MUST reject any credential whose recomputed proof does not match.

When present, the atpPqProof JWS MUST be verified independently, and a verifier that requires post-quantum assurance MUST NOT treat a valid classical proof alone as sufficient.

Verification and trust derivation

A verifier MUST: (1) confirm the structural requirements above; (2) obtain the issuer's public key(s) by resolving the issuer identifier; (3) verify the eddsa-jcs-2022 proof; (4) verify the atpPqProof when present and post-quantum assurance is required; and (5) reject the credential if an expirationDate is present and in the past. Only after all required checks pass MAY a verifier derive and act on the asserted trust score.

Security and Privacy Considerations

A TrustCredential is a third-party assertion. Relying parties MUST NOT treat a high trust score as authorization on its own; trust scores feed policy, they do not replace it. Verifiers SHOULD weight a credential by issuer reputation and by the reported confidence.

Because a trust score can reveal interaction patterns, issuers SHOULD mint short-lived TrustCredentials (via expirationDate) and SHOULD consider pairwise issuance to limit correlation. Selective-disclosure and unlinkability mechanisms are out of scope for this version (see the ATP privacy work).

Proof of Concept

A reference implementation issues and verifies TrustCredentials end to end with real cryptography (Ed25519 + FIPS 204 ML-DSA-65), including: round-trip issue/verify, rejection of a tampered credentialSubject, rejection under a wrong issuer key, rejection of an expired credential, and dual-proof (classical + post-quantum) verification. The score consumed by the credential is produced by the same four-factor engine defined in Trust Scoring Model.

Open Items and Conformance Gaps

  • Revocation / credential status. No status-list or revocation mechanism is defined yet. A verifier that encounters a credentialStatus property MUST NOT silently ignore it; the reference implementation treats its presence as a verification failure pending a future status profile.
  • Issuer key discovery. This version assumes the verifier resolves the issuer DID out of band; a normative binding to a specific resolution path is future work.
  • Selective disclosure. Disclosing individual factors without revealing the whole score is deferred to the ATP privacy mechanisms (pairwise DIDs, selective disclosure, ZKP).
